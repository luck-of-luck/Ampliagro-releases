## OS ACHADOS, POR ORDEM DE GRAVIDADE

### 1. `amplia_mcp/__init__.py` — a mentira que entra na cabeça da IA

```python
except Exception:
    pass
...
if not partes:
    return "Sem dados de contexto para este usuario."
```

Este não engole nada: **constrói o estado de falsidade**.

A IA recebia *"Sem dados de contexto"* e concluía que o produtor não tinha
propriedade nenhuma. O que tinha havido era um `OperationalError` — uma
coluna em falta a meio de uma migração.

O painel mente a um produtor. Aqui a mentira entra **na cabeça de uma IA que
lhe responde como se fosse verdade**. Um produtor que pergunta *"quais são
as minhas propriedades?"* recebe *"não tem nenhuma"* e desiste. Não há forma
de desconfiar: a resposta parece uma leitura de base.

**Correcção:** registado o que falhou, e **dito no contexto** que a IA
recebe — `[INDISPONIVEL: as propriedades não podem ser lidas neste momento
— isto NÃO é 'não tens isto', é 'não consegui verificar']`.

### 2. `production.py` — verificação de **cargo** a falhar para o lado permissivo

`TarefaEstagioViewSet.mover` (arrastar cartão no kanban):

```python
try:
    ... verificação de fazenda + cargo ...
except Exception:
    pass
tarefa.save()
```

Um erro dentro da verificação dava a **qualquer pessoa autenticada** o
direito de mudar o estado de uma tarefa, devolvendo `200 {"ok": true}`.

Não era um ataque elaborado. Era um operador sem `PerfilUsuario`, um
`permissoes` que é string em vez de dict, ou uma coluna em falta.

**Correcção:** 503 + log que diz o que a versão anterior gravava.

### 3. `middleware.py` — tenancy fail-open (o mais caro de todos)

```python
except Exception:
    # ... registava o erro e deixava passar
    # o proprio log admitia: "cross-tenant pode passar"
```

**MEDIDO:** cinco migrations por fazer fzeram o código pedir
`cod_municipio` a uma base sem a coluna. O `OperationalError` foi engolido,
o middleware ficou **silenciosamente inútil**, e desativou-se a si próprio.

O log estava lá, a dizer que corria mal. Ninguém lê um log e depois responde
*"muito bem, então passem os dados"*.

**Correcção:** 503 com mensagem que diz *"não é possível confirmar a que
propriedade este pedido pertence"*.

### 4. `user.py` — `alertas_list: []` quando o real era um erro

O produtor via **zero alertas** quando o que tinha havido era um erro de
base. Um `[]` diz *"não tens alertas"*; um erro diz *"não consegui ler"*.

### 5. `custos.py` — `except Exception: continue` onde só há `TypeError`

Estranhado para `(TypeError, ValueError)`. Com `Exception`, um
`OperationalError` era lido como *"esta linha do extrato não tinha data"*,
e a transação desaparecia da reconciliação sem ninguém saber.

## A RAIZ DE TUDO: "ENGOLIR UM ERRO É A FORMA MAIS FÁCIL DE DIZER ZERO"

Esta é a única ideia que valeu o dia.

Cinco bugs diferentes, a mesma gramática:

um valor só é "dado" quando tem fonte.

## A INVARIANTE (`aee0017`)

Escrevi `test_permissao_nao_falha_para_o_lado_permissivo`. Encontrou **8
sítios**, todos corrigidos.

O que a torna útil não é o que ela apanha hoje — é o que apanha **amanhã**,
quando alguém meter um `except: pass` à volta de uma verificação e não
estiver a olhar.

**Os 3 `pass` que ficaram** estão listados com a evidência lida:

```
production.py L191  dentro:   registro__user=prop.user
                      fallback: registro__user=user
                      os DOIS filtram por registo__user

production.py L216  o except cai para o bloco SEGUINTE, que volta a
                      verificar com pk= E user=, e levanta
                      PermissionDenied. A verificação acontece 2 vezes.

production.py L263  dentro:   Q(propriedade=prop) | Q(funcionario__user)
                      fallback: estagio__registro__user=user
```

Um `except: pass` onde o fallback é **mais estreito** não dá dados a
ninguém. Não os apaguei em silêncio — estão no teste, com a razão, para
que quem mudar o fallback tenha de vir tirá-los.

## O QUE EU NÃO FIZ, E PORQUÊ

### Não escrevi o teste de execução do `mover` na primeira vez

Escrevi um teste **estrutural** (lê o fonte, confirma que `status=503`
existe). Não prova comportamento. Escrevi-o na mesma noite, corri, e achei-o
suficiente. **Não era.**

Só ficou provado em `172244b`, quando o `get_queryset` deixou de engolir e
o caminho passou a ser alcançável. E a verificação que fecha o ciclo:

```
revertido (raise -> pass)   2 falhas
restaurado                  0 falhas
```

Um teste de fonte vigia **o ficheiro dele**. Um teste de execução vigia
**o caminho**.

### Suspeitei de uma fuga que não existe

`Q(cargo_alvo__iexact=perfil.area_servidor)` não filtra por dono nenhum,
num `OR` com cláusulas que filtram. Parece fuga. Medi **três vezes**:

1. tarefas com `propriedade` → sem fuga
2. criadas sem `propriedade` → os sinais preenchem
3. `bulk_create` (não dispara sinais) → `propriedade` fica NULL, **mas
   `get_queryset` devolve 0 tarefas**

Base real: **7 tarefas, 0 sem propriedade**.

**Conclusão: redundante, não perigoso.** E ficou registado como *risco
latente*, não como bug — porque se um dia um `bulk_create` deixar o campo a
NULL, essa cláusula alarga o queryset.

Deixei o código quieto. **Mexer em tenancy sem um bug demonstrado seria
inventar um achado** — exactamente o defeito que ando a corrigir.
