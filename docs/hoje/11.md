## 1. O que este dia foi

O pedido repetido foi: escolher o mais recomendado, e depois garantir que não há
brechas. A parte difícil não foi escolher — foi que **"garantir que não há
brechas" não é uma coisa que se possa garantir.**

Não é retórica. Neste dia encontraram-se **quatro** brechas, e duas delas estavam
*dentro da correcção da anterior*. Uma garantia de que não há brechas seria uma
menta: quatro breaches provam que a frase é invérida.

O que se fez, então, foi medir e declarar. Este ficheiro é o registo do que foi
medido, do que não foi, e do que ficou por fazer.

Antes de escolher o que construir, calculei onde o Ampliagro é **provadamente**
melhor. Cruzamento entre o que só ele tem e o que a matriz prova que os

Contra a TOTVS no backoffice e contra a Aegro no financeiro, o Ampliagro perde —

O problema encontrado ao ir por aí: **a autonomia que eu tinha construído era
invisível.** Os alertas iam para a base de dados; o produtor só sabia se abrisse
a aplicação. Um alerta que ninguém recebe não é autonomia, é uma tabela.

**X06: N → E.** `app/services/whatsapp.py`, cliente da Meta Cloud API. Escolhi a
API oficial e não Evolution/Baileys: as não-oficiais automatizam o WhatsApp Web,
violam os termos da Meta (ban sem recurso) e são o "número plausível sem nada
por trás" que este projecto recusa — agora com o telefone de um agricultor real
no meio.

O atrito real, dito com as palavras da plataforma: a Meta **não permite iniciar
conversa**. Um alerta proativo cai exactamente no caso proibido, logo depende de
template aprovado. Sem `WHATSAPP_TEMPLATE_ALERTA`, não envia — e diz porquê.

Ficou em **E, não C**: a coluna pede *interface*; o que existe é alerta de
*saída*. Falta `receber()`.

## 3. As quatro breaches

### 3.1 — O porto de entrada não via corpos JSON

`app/middleware.py`:

```python
fonte = request.GET if request.method == "GET" else request.POST
```

`request.POST` do Django **só** é povoado para formulários. Numa API DRF, quase
todo o POST/PUT vai como `application/json` — e então `fonte` chegava vazio, o
`continue` saltava cada chave, e **a verificação de tenancy não corria**.

É o *único* porto de entrada do isolamento multi-empresa, desligado **em
silêncio**: sem excepção, sem log, sem 500.

Corrigido com `_corpo_json`, que lê o corpo só quando o content-type é JSON — o
content-type é testado *antes* de ler, porque num multipart ler o corpo consome
o stream e a view fica sem ficheiro.

### 3.2 — A confirmação confirmava contra uma mentira

`app/ia/texto.py::prompt_de_confirmacao(spec)` recebia **só** a definição
estática do intent. Os valores que o produtor escreveu nunca chegavam lá.

Medido nos **33** intents que anunciam `prompt_confirmacao`: **zero** tinham
espaço para o valor, e **os 33** tinham texto fixo. A prova:

```
"Apagar a safra soja 2026/27?"   ← FIXO
```

Saía **idêntica para qualquer safra**. Quem pede para apagar a safra 2025/26 lê
uma pergunta sobre 2026/27, diz "sim", e 2025/26 desaparece. Não há como saber:
o valor recolhido só existe na base de dados.

É a mesma doença do alerta que mentia, na fronteira mais grave do sistema. Um
alerta que diz "conta vencida" é um susto errado. **Uma confirmação que diz
"apagar soja 2026/27" é uma destruição autorizada contra uma mentira.**

Corrigido: textos com `{campo}` são preenchidos, e os 33 textos fixos **ganham
automaticamente** a linha do objecto — sem editar um ficheiro. Campo vazio
escreve **"não informado"**, não desaparece.

### 3.3 — A correcção anterior lia a chave errada

Ao procurar o item seguinte, medi:

```
corpo DRF   {"talhao": 2}     → 404   (o middleware NÃO recusou)
corpo cru   {"talhao_id": 2}  → 403   (o middleware apanhou)
```

O middleware procurava `talhao_id`. Um serializer DRF espera **`talhao`**.

Ou seja: **a correcção 3.1 era necessária mas não suficiente.** Tornou o
middleware uma barreira real para corpos JSON, mas uma barreira que não olha
para o campo que o serializer lê. Para a API — que fala JSON — a verificação de FK
continuava desligada.

Corrigido: para cada `X_id`, verifica também `X`.

### 3.4 — A barreira de autorização estava fora do serializer

O caso que abriu a caça: `AplicacaoInsumoSerializer` não tem `validate_talhao`.
A sua view tem `get_queryset()` — mas **`create` não passa por `get_queryset()`**
em DRF. O serializer não valida. Depende do middleware.

O inventário mediu o que eu suspeitava, e o que não suspeitava:

| | |
|---|---|
| campo de dono gravável, **com** guarda no serializer | **25** |
| campo de dono gravável, **sem** guarda | **37** |
| o caso que eu tinha encontrado | 1 de 37 |

Os piores escrevem **directamente** em `propriedade`: `ContaBancaria`,
`Parcelamento`, `Racao`, `TarefaEstagio`, `TelemetryData`. O cliente escolhe a
fazenda.

A diferença entre 25 e 37 não é o número. É **de quem depende a garantia** — e
aquela linha de middleware já demonstrou, duas vezes, que pode ter lapse sem
ninguém dar por isso.

`app/api/ownership.py` — `OwnershipMixin` com `dono_pelo_campo`. A cadeia
(`safra` → `talhao.propriedade.user`) escreve-se **uma vez**, não 37. Aplicado a
`RacaoSerializer` e `TarefaEstagioSerializer`.

E o mais importante não é o mixin: é **`tests/test_nenhum_serializer_escreve_na_fazenda_de_outro.py`**.
Não é um teste, é um inventário vivo, e é bidireccional:

- serializer novo sem guarda → **vermelho**, a menos que alguém o declare com a
  razão escrita;
- entrada morta na lista → **vermelho**.

Os 37 estão declarados um a um, com a razão de cada um. **A lista não cresce por
silêncio.**

## 4. Mutation testing: a parte que vale mais

Um teste que nunca falhou não prova nada. Inyectei a mutação de cada correcção
para ver se os testes a apanhavam. O resultado apanhou-me a mim, quatro vezes:

| Mutação | Resultado | O que revelou |
|---|---|---|
| voltar a ler só `X_id` | **não apanhada** | o teste só fazia `print`; um teste que imprime e passa na mesma não mede nada |
| desfazer a ligação `sandbox` → `prompt_de_confirmacao` | **não apanhada** | os testes chamavam a função directamente, com os parâmetros à mão — não provavam que alguém lha passasse os valores |
| serializador novo sem guarda | **apanhada** | o inventário vivo funciona |
| desactivar `validate_*` da confirmação | **apanhada** | |

Total, por correcção: **7/7** na confirmação (depois do teste ponta a ponta),
**2/3** nos nomes de campo (1 equivalente, 1 inexplicada), **1/1** no inventário.

Três vezes nesta sessão um teste passou **pelo motivo errado** — resultado certo,
medição errada. Três vezes eram testes meus. Vale mais registar isto do que
registar os quatro breaches.

## 5. Os meus erros, contados

Nenhum se escusa. Vários foramwritten; ficam escritos porque é deles que sai a
lição.

**Instrumentos que mediam a estrutura errada.** Escrevi três antes de medir uma
coisa, e os três estavam errados:

| O que procurei | O que encontrei | Porquê |
|---|---|---|
| Viewsets | **0** | `viewsets.ModelViewSet` é `ast.Attribute`; eu só lia `ast.Name` |
| Viewsets com escrita | **3** | 50 herdam `create` de `ModelViewSet` — não estão em `def create` |
| Serializers sem `fields` restrito | **1** | o `Meta` é `ast.ClassDef`; eu só lia `ast.Assign` |

Só quando mexi a ler directamente é que a resposta apareceu.

**Cinco campos de modelo adivinhados.** `Talhao(area=)`, `Cultura(slug=)`,
`Safra(cultura="SOJA")` (é ForeignKey para `Cultura`, não string),
`Safra` sem `propriedade`. É exactamente a disciplina que este projecto exige
das âncoras — ler a linha, não supor o nome — e que eu não apliquei às fixtures.

**Um `NameError` dentro do `try` do middleware.** O `import json` não entrou na
primeira escrita. Se tivesse chegado ao runtime, era uma excepção dentro do
`except Exception` do TenantIsolationMiddleware — o caminho que aquele ficheiro
descreve como o modo de falha mais caro.

**Classes `O...Test`.** `exit=5`: **zero testes recolhidos**, e eu tardei a ver.
O ficheiro não media nada.

**`self.assertEqual` em classe pytest pura.** Duas vezes. `JsonResponse` não tem
`.json()` (é do `requests`). DRF exige `.is_valid()` antes de `.errors`.

**Um `import` meu que mudou o comportamento por engano:** o `OwnershipMixin`
usava `__getattr__` (de instância); passou a `__init_subclass__`, que gera os
validadores reais na classe.

**Uma contradição no meu próprio código.** O docstring de `resumir_valores` dizia
*"um campo vazio escreve 'não informado', não desaparece"* e o código logo abaixo
fazia `v not in (None, "")` — que o deita fora. Contradição no ponto exacto que
eu escrevi para não acontecer.

**Dois erros meus que o teste novo apanhou:** `ComandoDeviceSerializer` na lista
com guarda já existente, e `PropriedadeSerializer` declarado sem guarda quando
já estava protegido por `HiddenField(CurrentUserDefault)`. O segundo levou três
tentativas a diagnosticar: `str(getattr(cls, campo))` dá `None`, porque o DRF
tira os campos declarados do namespace e os mete em `_declared_fields`.

**`+55` devolvia vazio.** Em `normalizar_e164`, comparei os dígitos com o código
ISO (`BR`) em vez do código de chamada (`55`). O número que um produtor escreve
correctamente era o único que não funcionava.

**Encontrei-o tarde demais:** a mutação da propriedade no request ficou por
explicar. O ficheiro mutado foi confirmado em disco e visível num processo novo,
e o resultado não mudou. Registado como inexplicado, com a tentativa de
diagnóstico escrita, em vez de uma explicação inventada.

## 6. Scanners: o que mediram e o que não mediram

| Scanner | Resultado | Veredicto |
|---|---|---|
| `hardcoded_secret` | **84 "high"** | **84 ruído, 0 reais** — todos `password='x1234567'` em fixtures; **zero** em código de produção |
| injecção (sql/cmd/xss) | 0 achados | **`files_scanned: 0`** — inútil, descartado |
| injecção manual, 353 ficheiros | 3 padrões | 3 limbos, 0 reais |

O scanner de injecção **não leu um ficheiro e devolveu "0 issues"**. Esse
resultado é pior que um achado: parece um verificador e não é. Fiz a leitura à
mão. O que apareceu foi um `.extra(select={f"date_trunc('{trunc}'…)"})` perigoso
*por construção* mas com `trunc` limitado a `"hour"`/`"day"` duas linhas acima;
`mark_safe` cujo `inner` só pode vir de um dicionário com `_default`; `getattr`
iterando `dir(mod)`, não input externo.

Um padrão que casa pelo *nome do argumento* não distingue
`password="x1234567"` de `AWS_SECRET_ACCESS_KEY=`. O que falta não é mais
padrões — é contexto.
